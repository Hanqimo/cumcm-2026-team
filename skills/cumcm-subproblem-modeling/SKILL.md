# 逐小问建模研究

## 1. 目的与协作方式

围绕当前小问，形成符合题意、数学表述完整、计算可复现、验证证据可信、便于后续小问继承的解决方案。

全队共同研究同一个小问，处理完当前小问后再进入下一问。允许在当前小问内部并行研究候选模型、算法和验证方法，不按小问设置固定负责人，不使用编辑锁。

研究是可以反复进入的过程。根据本轮请求选择工作阶段，不机械地从头重做，也不自动一次性完成全部阶段。

## 2. 与题意理解 Skill 的衔接

优先承接 `math-modeling-problem-framer` 已有的分析，包括整体图景、材料清单、各问依赖、事实与假设、变量、约束和基础模型结构。

已有分析是研究依据，不是不可质疑的结论。对影响当前小问的定义、条件和公式，应回到题面或附件核对。

如果没有已有分析，补齐当前建模所必需的整体理解和材料阅读。不得因为缺少第一个 Skill 的输出而停止，也不得在整体目标尚不清楚时直接套用模型。

已经确认阅读过且未变化的材料可以复用记录；新的附件、修订数据、争议图表和关键题意必须重新检查。说明未读取或无法访问的材料及其影响。

## 3. 本轮范围与阶段选择

开始时用简短文字说明当前小问、本轮任务和停止边界。

- 回顾：恢复已有状态，说明结论、依据、分歧和下一步。
- 模型分析：提出有竞争力的模型，完成数学表述和算法类型分析，不运行求解。
- 算法设计：核对模型后给出可实施算法、约束处理、复杂度和验证计划，不自动执行计算。
- 求解：完成必要检查、成本估计、实现和运行，进行基本数值检查；尚未完成独立验证的结果明确标为待验证。
- 验证：独立检查模型与计算，报告证据和差异，不默默改写原方案。
- 改进：提出有依据的改进方案；只有用户要求实施时才修改模型或代码。
- 完整解决：在授权范围内依次推进，遇到实质性歧义或验证冲突时先解决问题。

“继续”应从上轮未完成的位置恢复。“继续讨论”不自动表示执行计算。“先不求解”等阶段边界持续有效，直到用户改变要求。

必要的前置核查可以进行，但不能借此扩展到下一小问。完成当前阶段后停止，不要求用户重复确认已经明确授权的操作。

## 4. 恢复研究基线

先定位仓库根目录，阅读当前 README、协作规范和适用的项目指令，再按需读取以下信息。

1. `contest/STATUS.md` 和当前小问的 `state.md`。
2. 全局符号、假设、依赖和重要决策。
3. 前序小问的 `adopted.md` 及其正式输出。
4. 当前小问的决策记录、模型比较和采用方案。
5. 本轮涉及的模型表述、代码、配置、运行清单和验证记录。
6. 与当前争议直接有关的历史讨论或 Git 差异。

不要每轮遍历全部论文库、所有运行结果和所有历史对话。先读状态入口，再沿相关文件路径追溯证据。

恢复后说明：

- 当前小问要求什么，输入和输出是什么。
- 已有模型及其关键假设。
- 已尝试的算法、结果和验证程度。
- 从前问继承了哪些结果、假设与误差。
- 团队已经决定什么，哪些只是候选意见。
- 当前缺口及本轮准备解决的问题。

记录之间发生冲突时，回到题面、模型、代码或运行证据核对。不能仅凭文件更新较晚，或者位于 `main`，就认定内容正确。

未访问远程时，不声称已经掌握队友最新进展。

## 5. 证据与结论分类

沿用题意理解阶段的分类：

- `[题目事实]`：题面、图表或附件明确给出。
- `[题意推断]`：由题目事实推得，并说明依据。
- `[建模约定]`：符号、方向、统计口径等人为选择。
- `[拟采用假设]`：有依据但仍需检验的简化。
- `[候选假设]`：证据不足，尚不能默认采用。
- `[背景知识]`：来自题面以外的专业知识。
- `[未决歧义]`：存在会影响方案的不同解释。

另外分别记录验证状态与采用状态。

验证状态可以是“未检验”“初步检查通过”“独立验证通过”“存在冲突”；采用状态可以是“候选”“推荐”“团队采用”“已否决”“已被替代”。

验证通过不等于团队采用，团队采用也不等于假设已经成为事实。不得将助手的推荐写成已经达成的团队共识。

## 6. 模型分析

先用自然语言解释问题的物理、几何、统计或决策含义，再给出符号与数学表述。

重点核对目标、指标定义、单位、对象范围、时间空间尺度、硬约束、软偏好以及前问输入的适用条件。比例或效率必须说明分子、分母和统计范围。

从原始对象或机制确认公式的适用条件，不将特殊情形的公式直接推广到当前问题。

保留真正有竞争力的候选模型，不规定必须凑足数量。简单问题可以只有一个方案；存在重要取舍时，比较少量合理备选。

对每个保留模型说明：

- 直观思路及其与题意的对应关系。
- 已知量、未知量、变量角色、单位和取值范围。
- 完整数学关系与参数来源。
- 新引入的假设、约定和简化。
- 优点、缺点、适用范围和失效情形。
- 数据是否足以识别或估计所需参数。
- 计算与验证是否可行。
- 适合的算法类型及初步理由。

按模型类型补齐必要内容。

- 优化模型包括决策变量、优化方向、目标函数、可行域、约束和多目标处理方式；权重、罚项与阈值必须说明来源。
- 机理模型包括状态、作用关系、方程、参数、初始条件和边界条件。
- 统计模型包括观测单位、目标量、解释变量、估计方法、数据划分、评价指标和不确定性。
- 仿真模型包括实体、状态、转移规则、随机机制、输入和统计输出。
- 几何或图模型包括对象、坐标或节点边定义、关系以及成立条件。

比较应围绕题意符合度、额外假设、解释性、可识别性、计算代价和可验证性展开。复杂程度或算法名称本身不能作为优越性的证据。

模型分析结束时，说明推荐方案、推荐依据，以及什么新证据可能改变推荐。

## 7. 算法设计

算法必须对应已经明确的模型版本。模型尚未确定时，可以分别给出适配方案，但不能假装已经选定唯一算法。

先诊断影响算法选择的结构，包括变量类型、维数、线性或凸性、光滑性、约束、稀疏性、可分解性、多峰、对称性、噪声和单次计算成本。

能够利用结构时，优先考虑解析推导、消元、枚举、动态规划、图算法、线性或整数规划、凸优化及专用数值方法。

采用模拟退火、遗传算法等启发式方法时，必须说明需要它的具体原因，不能仅因算法常见或优秀论文使用过就选用。

设计内容应足以让用户或另一位队员实现：

- 输入、输出和解的表示方式。
- 核心步骤及必要的伪代码。
- 初始化、变量尺度和参数设置。
- 硬约束检查、可行性维护或修复方法。
- 停止条件、失败标准和输出诊断。
- 时间、内存及主要计算瓶颈。
- 基线、参照解或质量界限。
- 独立验证方法。

罚函数较小不能代替原始硬约束满足。最终候选解必须回到原约束逐项检查。

改进算法必须针对已识别的结构或瓶颈，解释修改机制、预期收益和额外成本。需要验证改进贡献时，在相同输入、评价指标和合理一致的预算下与基线比较，并进行必要的消融试验。

对简单问题，解析解或小规模精确解可以同时充当基线或参照，不强行实现多套复杂算法。

## 8. 计算预算与执行

执行明显耗时的计算前，估计规模、时间、内存、依赖软件和主要不确定性。能进行小规模试运行时，用其耗时校准估计；否则给出有依据的范围，不编造精确时间。

分别说明计算机运行成本与 AI 交互成本。不能把工具调用次数直接换算为账户额度，也不能承诺由用户运行代码一定节省多少额度。

先进行小样例和可行性检查，再扩大规模。明确最大运行时间或迭代预算、终止条件以及必要的检查点，避免无界搜索。

耗时过长时，依次考虑利用结构、分解、缓存、近似、降低精度或调整算法，再判断模型是否需要简化。任何简化都应说明对题意和结果的影响。

由用户执行时，提供完整代码、依赖说明、运行目录、命令、输入输出路径、参数、种子、预计耗时及应返回的诊断信息。未取得实际输出前，不得声称已经运行或验证。

## 9. 求解记录与可复现性

运行前核对输入、单位、坐标方向、数据处理和输出路径。原始文件保持不变，已有重要输出不得静默覆盖。

每次重要运行记录：

- 小问及模型、算法、数据版本。
- 输入文件路径和必要的校验值。
- 实际执行命令、工作目录和配置。
- 依赖版本、随机种子和运行环境。
- 起止时间、停止原因、目标值、残差与约束违反量。
- 输出文件及验证状态。

Git 提交编号应指向实际使用的代码。代码含未提交修改时，必须标明工作区有改动，并保存相关差异或源文件快照及校验值；不能只写 HEAD 就声称可复现。

不把求解器正常退出等同于正确求解，也不把算法停止等同于获得全局最优。

按照数据精度和误差报告有效数字，保留必要中间量。未完成独立验证的结果明确标为待验证。

## 10. 独立验证

每个准备采用或报告结果的模型，都必须有适配其主要风险的验证方案。尽量在看到最终结果前确定关键检查和容差。

验证覆盖两类不同问题。

第一类是模型是否准确表达题意。检查指标定义、约束、公式条件、量纲、边界、极限、机制与假设，并选择有区分力的例子检验。

第二类是计算是否正确实现模型。采用不同表示、推导或求解路径，尽量避免与主方法共享关键错误来源。

同公式换语言重写、同函数重复调用、更换随机种子、程序成功退出和图形平滑，都不能单独构成独立验证。更换求解器可以帮助核对数值求解，但不能证明双方共享的模型正确。

按需要选择证据：

- 几何模型用直接构造、相交或距离计算核对闭式公式。
- 小规模离散问题用穷举或精确解核对。
- 优化问题检查原始可行性、界限、最优性间隙和适用条件下的最优性条件。
- 微分方程或积分检查解析特例、守恒性质及步长或网格收敛。
- 统计模型检查数据泄漏、划分方式、残差、样本外表现和不确定性。
- 随机仿真检查已知情形、重复试验和统计误差。

严格区分可行解、局部最优解、当前最好解和有证据支持的全局最优解。非凸问题中的 KKT 条件通常只能作为必要条件检查；多次运行得到同一结果也不是全局最优证明。

为用户提供可人工核验的证据链，包含检查目的、输入、关键公式、代入过程、中间数值、预期性质、实际差异、容差依据和结论。至少给出一个代表性计算点；全局性质不能由少量抽查代替。

如果验证冲突，先定位定义、假设、推导、实现、输入或数值精度方面的原因。未解释冲突前不得宣布验证通过。

如果当前任务只是验证，保留被审查版本并报告修正建议；如果用户已授权修复或完整求解，可以建立修订版本并重新核验。

不存在充分独立的验证路径时，应如实报告已有证据及其覆盖范围，不能用“验证通过”掩盖缺口。

## 11. 批判分析与迭代

完成计算核查后，分析当前方案真正存在的不足，而不是套用通用优缺点。

结合题目考虑假设敏感性、参数误差、前问误差传播、数值稳定性、算法预算、数据代表性、推广能力和解释性。

每个值得实施的改进应说明：

- 具体缺陷及证据。
- 拟修改的模型或算法内容。
- 预期收益与额外假设。
- 所需时间和计算成本。
- 如何验证，以及何时认为改进值得保留。

复杂后问可以比较更多结构和稳健性方案。简单前问若已得到直接、完整、可核验的解法，应明确说明无需额外复杂化。

修改关键假设、目标或约束后，应更新模型版本，并重新检查受影响的计算与验证。不能沿用旧版验证状态。

## 12. 仓库记录与安全保存

以当前仓库 README 和协作规范为目录及 Git 工作流依据，不在 Skill 内复制整套 Git 教程。

本仓库中的记录分别承担以下职责：

| 路径 | 记录内容 |
|---|---|
| `contest/qN/state.md` | 当前研究状态与下一步 |
| `research-log.md` | 尝试过程及失败发现 |
| `decisions.md` | 已达成的决定与理由 |
| `comparison.md` | 有竞争力模型的比较 |
| `adopted.md` | 团队正式采用方案的入口 |
| `models/<model>/` | 模型、代码、配置、运行及验证 |
| `exports/` | 当前小问正式输出 |
| `contest/global/accepted-results/` | 跨小问共享的正式接口 |
| `contest/global/dependencies.md` | 前后问之间的依赖 |
| `contest/STATUS.md` | 全队集成进度 |

纯讨论时在对话中交付，不自动落盘。已授权本地实施时，同步更新本轮实际影响的记录，不机械地改写所有状态文件。

研究分支上的结论默认是候选或推荐。未经团队确认，不修改正式采用入口或把候选结果发布为全局结果。短分支状态不得直接冒充集成分支上的全队状态。

重要结果尽量保留唯一来源。`exports/` 和全局接口优先使用来源清单引用同一份结果；必须复制时，记录源路径、提交及校验值，避免多个副本分别修改。

写入前检查当前分支、已有修改、暂存内容、未跟踪文件和目标路径。保护用户与队友已有工作，不使用编辑锁，不覆盖同名未知成果。

遵守当前授权的保存级别。写文件不自动表示提交，提交不自动表示推送或合并。已经明确授权的操作不重复询问。

## 13. 小问完成与向后传递

分别记录以下完成程度，不要求每轮重新走完全部阶段：

- G0：题意、指标和输入输出明确。
- G1：模型数学表述完整，假设与风险清楚。
- G2：算法匹配模型，预算和停止条件明确。
- G3：实际计算完成且可复现。
- G4：独立验证完成，冲突已解释。
- G5：不足、适用范围和有价值的改进已评估。

这些是质量状态，不是每一步都必须请求批准的审批流程。简单问题的 G5 可以得出“暂无值得增加的改进”。

达到本轮要求后停止。即使当前小问已完成，也不自动开始下一问或执行 Git 合并。

当用户要求正式完成并发布本小问时，交付完整模型、算法、结果、验证证据、适用范围和复现入口。传递给后问的结果同时携带假设、误差、数据版本和来源提交。

若前问后来修订，应将受影响的后问结果标记为待复核，并列出需要重算或重新验证的部分。保留旧版本和旧完成标签。

## 14. 输出方式

使用连贯段落解释，先讲直观含义，再给数学表述和证据。短公式优先放在行内，中文句子中不得在行间公式前使用冒号。

本轮输出按实际需要包含当前基线、核心工作、验证或风险以及下一步，不机械重复所有章节。给出可人工核查的推导和中间量，不只提供最终数值。

结束时用简短状态说明交代：

- 当前小问和本轮完成阶段。
- 新增结论及其验证、采用状态。
- 尚未解决的问题。
- 如有落盘，列出文件及提交、推送状态。
- 下一轮最值得处理的事项。

首次独立建模从题面、附件和已有研究出发，不默认读取优秀论文中的现成解法。确需查阅背景或算法资料时，区分外部依据与独立推导；用户要求不联网时遵守该边界。
